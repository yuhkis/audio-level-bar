# Development reference

Use the section that matches the change. The product and safety boundaries that hold for every change are in [AGENTS.md](../AGENTS.md); the detail lives here so that a task loads the guidance it needs rather than the whole instruction set.

## Verification scope

| Change | Evidence to collect |
| --- | --- |
| Documentation or instructions only | The diff, the links and anchors it contains, and consistency with the documented commands and behavior |
| UI-independent level calculations | `make test`, the unit tests for those calculations |
| User-facing text | `make check-localization`, plus an app check when the display or the layout changes |
| Core Audio, permissions, devices, or volume writes | The automated checks that apply, and the real-device cases below |
| Build, bundle, signing, or a deployment candidate | `make ci` and candidate verification, plus real-device checks for the behavior the candidate changes |

`make ci` builds the app bundle, so the build-number rule below applies to it whatever the change was; read that section before running it in a checkout that still holds a candidate in `dist/`.

## Audio verification

- Before Core Audio changes, run `make test` and `make diagnose` when practical to establish a baseline. `make diagnose` must stay read-only: it enumerates the real devices and their control capabilities without altering volume or the selected devices.
- GUI, microphone permission, device switching, and volume writes require explicit real-device testing. Preserve the original default devices, volume, and input gain before a write test, and restore them afterward.
- Test built-in audio first, then the connected external or virtual devices that matter to the change: a USB audio interface, a wireless microphone system, AirPods, Teams Audio, ZoomAudioDevice, and BlackHole. Include unplug/replug and sleep/wake for anything that touches device or resource lifecycle. Record which devices were unavailable and which cases went untested.
- Anything that creates and destroys Core Audio resources repeatedly has to be exercised well past the point where it starts passing, and the cycle count reported, unless every cycle is judged from logs that show the failure mechanism itself, as the hardware gate below does. A change that rebuilt the published microphone's aggregate device on every idle transition passed the few consecutive sessions its verification happened to use, then failed shortly after in a way that left the device missing from every app's input list, and was reverted. A few passes in a row do not close this.
- Never destroy an aggregate device while another process has it open, in the app or in a throwaway experiment. Read `kAudioDevicePropertyDeviceIsRunningSomewhere` first. A wedged `coreaudiod` stops answering any process on the machine, and while SIP is enabled the only way back is a restart.

For processed-microphone changes, select the affected cases from [DESIGN.md's real-device verification](../DESIGN.md#加工済みマイクの実機検証), and preserve its contracts for the physical default input, the opt-in, consuming apps, idle, and teardown. The [known limitation](../README.md#known-limitation-a-second-open-in-the-same-process-is-silent) records why rebuilding the publication on every idle transition was withdrawn; do not reintroduce it.

### Hardware gate procedure

The ROADMAP gate for unplugging, Bluetooth headsets, and sleep/wake is judged per cycle from logs rather than from survival. A hazard that strikes on only some of the risky operations can pass a run of survival cycles by luck, and a `coreaudiod` wait can stall every process without ever turning into a hang, so surviving cycles prove little either way. What the device-bound IOProc meter and the quiet window remove shows up directly in each cycle's log instead: IO by the app on a Bluetooth input or output, an app call in flight when a Bluetooth pause burst begins, an app lifecycle call inside a quiet window, a configuration change that stalls on its way to the driver. The criteria below therefore show, in every cycle, that the mechanism is absent, and the gate does not rely on accumulating cycles to catch a rare race; that is why the cycle counts are small. [ROADMAP.md](../ROADMAP.md#次のゲートのログ合否基準) records the same criteria and checks in Japanese. The procedure exercises real devices, and a failure can take a restart of the Mac to recover, so do not run it with unsaved work or before a call.

#### Before the gate

1. Commit, build, and verify the candidate ([Build and installation](#build-and-installation)), install it with `make install`, and launch the installed copy in `/Applications`. The gate judges that installed app, not `dist/` or `swift run`.
2. Run `make test` and `make diagnose`, and record the baseline default devices, volumes, and input gain, to restore afterwards.
3. Start only in the long-uptime state: at least four hours since boot, with everyday apps running. There is no fresh-boot block.
4. Use one Bluetooth headset that connects when it leaves its case and disconnects when it goes back. Disconnect every other Bluetooth or Bluetooth LE audio device for the whole gate: one that stays connected keeps Apple voice processing off in ③b-Apple and adds configuration changes of its own to the cycles. Quit apps that could open a microphone during a cycle, such as calls, dictation, or a browser tab using the microphone, except where a scenario below opens one on purpose.
5. Have QuickTime Player for the ③b recordings, and, for the ③b-off `third-party-mic` scenario, an app whose input can be set to the headset microphone without changing the default input.
6. After every Quit, wait until the process has exited, for example until `pgrep -x AudioLevelBar` prints nothing, before a relaunch or `make install`: the process can outlive its menu bar item by a few seconds.

#### Capture

For every block, start a live capture before its first cycle and stop it after the block's closing `make diagnose`. The persisted `coreaudiod` log at the default level rolls over within hours, so a `log show` afterwards cannot stand in for it. Run the commands from the repository root. Keep the captures under `.local/gate/`, which is git-ignored and does not exist in a fresh clone or worktree, in one file per block, so that starting the next block never truncates an earlier capture. `<config>` is `1`, `2`, `3a`, `3b-off`, or `3b-apple`, and `<block>` is a block name from [Configurations and blocks](#configurations-and-blocks) or [the scenarios](#scenarios-folded-into-the-configurations):

```console
mkdir -p .local/gate
/usr/bin/log stream --style ndjson --level debug --predicate '(process == "coreaudiod" AND (eventMessage CONTAINS "RequestConfigChange" OR eventMessage CONTAINS "PauseAllContexts" OR eventMessage CONTAINS "PauseIO" OR eventMessage CONTAINS "ResumeIO" OR eventMessage CONTAINS "restarting IO" OR eventMessage CONTAINS "Reconfigure of" OR eventMessage CONTAINS "BluetoothHALPlugIn_" OR eventMessage CONTAINS "HFPInputShimDevice" OR eventMessage CONTAINS "Start_ActivateDSP" OR eventMessage CONTAINS "NEGOTIATE" OR eventMessage CONTAINS "ADAPT" OR eventMessage CONTAINS "mIODisableCount" OR eventMessage CONTAINS "IOWorkLoopInit" OR eventMessage CONTAINS "IO Stopped" OR eventMessage CONTAINS "_StartIO" OR eventMessage CONTAINS "_StopIO" OR eventMessage CONTAINS "HALS_MultiTap" OR eventMessage CONTAINS "_Deactivate" OR eventMessage CONTAINS "still waiting" OR eventMessage CONTAINS "Sent device config change" OR eventMessage CONTAINS "StartIO block counters" OR eventMessage CONTAINS "StopIO: failed" OR eventMessage CONTAINS "Received power notification" OR eventMessage CONTAINS "NewState:" OR eventMessage CONTAINS "CADefaultDeviceAggregate" OR eventMessage CONTAINS "VPAUAggregateAudioDevice" OR eventMessage CONTAINS "Requesting config change" OR eventMessage CONTAINS "Starting config change")) OR (process == "AudioLevelBar" AND processImagePath BEGINSWITH "/Applications/Audio Level Bar.app/") OR eventMessage CONTAINS "StartAndWaitForState" OR eventMessage BEGINSWITH "ALB-GATE"' > .local/gate/<config>-<block>.ndjson
```

The app's clause takes only the installed bundle's executable: `make diagnose` runs a `swift run` build under the same process name, and its HAL client lines must not be read as the app's. The path survives the relaunches some blocks make, where a PID written into the predicate would not. When judging, the app's lines are those whose `processID` is the installed app's PID, which a marker records at the start of every block and after every launch:

```console
/usr/bin/logger "ALB-GATE <config> <block> app-pid $(pgrep -f '^/Applications/Audio Level Bar.app/')"
```

Mark the start and the end of every cycle, and each step a scenario below names, in the same log, so that each cycle can be cut out and judged on its own:

```console
/usr/bin/logger "ALB-GATE <config> <block> cycle <n> begin"
/usr/bin/logger "ALB-GATE <config> <block> cycle <n> <step>"
/usr/bin/logger "ALB-GATE <config> <block> cycle <n> end"
```

#### The app's log lines

Every line the app writes for the gate is one public string in subsystem `io.github.yuhkis.audio-level-bar`, category `hal-lifecycle` (`HALLifecycleLog`). A parser has to accept `|`, `?`, and `,` inside `transport=`, and `,` inside `reason=` and `pending=`.

Immediately before every IOProc, process tap, and aggregate device create, start, stop, and destroy, and every processed microphone `AVAudioEngine` prepare, start, and stop, once the call's generation check has passed, the app writes `<object> <operation>-begin id=<AudioObjectID> transport=<class> gen=<n|->[ reason=<word>][ output=<id>][ aggregate-uid=<uid>][ tap-uid=<uid>]`. Once the call has returned, it writes the same line without `-begin` and with `status=<OSStatus>` after the transport. The operations with a begin line are `create`, `prepare`, `start`, `stop`, and `destroy`. `prepare` is an engine's `prepare()`, which allocates its I/O unit and can already create the unit's IOProc on the bound device; its status is 0, or `kAudioHardwareUnspecifiedError` when the call raised. A begin line with no result line is a call that has not returned. The begin line of a process tap or aggregate device create has `id=0`, because the call assigns the ID.

The other operations have no begin line, and carry `status=0` unless stated:

- `refuse`: the device was not opened. The meter's and the capture's IOProcs write it only for a refusal on their lifecycle queue. With no `create` before it, the read immediately before the create refused. After a `create`, the read made once the listeners were in place, immediately before `AudioDeviceStart`, refused, and `destroy-begin` and `destroy` follow, or `interrupt` when a window armed since the start was issued. A default input the poll already refuses is not opened and writes no line. With `reason=bluetooth-sub-device`, an open aggregate device gained an active Bluetooth sub-device. `processed-microphone-publisher-engine refuse` means no output the publisher may be bound to (the ID and class are the default output's), or that the uncached re-read of a bound output that is not built-in, immediately before the engine is prepared and started, found it unreadable or involving Bluetooth; no prepare or start line follows for that engine. `processed-microphone-source refuse` is described with its object below.
- `open-unverified`: the device is opened although Bluetooth could not be ruled out, such as a transport reported as unknown. It can be written a second time after `create`, when the second read's note differs from the first.
- `interrupt`: a start issued before a quiet window armed, abandoned before this call. What it created stays until the next start or stop after the window. It can follow the `stop` or `destroy` lines of the release a start makes first; only the steps after those lines stay. Right after a failed start or a `refuse`, it means the release of what that start created waits for the window. `processed-microphone-capture-ioproc interrupt` after a `create` with no `start-begin` can also mean that the publisher's build failed once a window had armed: the unstarted IOProc waits for the release, and the failure is not reported, so the processing mode stays. The processed microphone's publication writes it on `processed-microphone-tap`, `processed-microphone-aggregate`, or `processed-microphone-probe-ioproc`, with `reason=before-<create|start|stop|destroy>` naming the call it held back, as described with those objects below.
- `interrupt-stop`: a stop issued before a quiet window armed, abandoned before this call. What it would have stopped stays, no longer reporting levels, until the next start or stop after the window. It can follow `stop` or `destroy` lines of the same release, whose objects are already stopped or destroyed. The processed microphone's engines write it too, one line for each engine kept, when the generation their stop was issued in is no longer current as the main thread is about to stop them: neither engine is stopped, no `stop-begin` of either follows until a release, and an owed `processed-microphone-aggregate destroy` does not follow either, because the publisher may still render into the muted tap. Apple voice processing has two engines, and the capture engine's stop can wait in `coreaudiod` while a change begins, so the generation is compared again before the publisher's stop: a window that arms inside the capture engine's stop leaves that engine stopped, with its stop lines, and the line is written for the publisher alone, which keeps rendering silence until the release. The release of a failed Apple start compares the same way between its two stops, and writes `interrupt` for the publisher it keeps. The rollback of what an interrupted publication kept writes it on the publication's objects, with the same `reason=before-<call>`.
- `stall`: a lifecycle call has not come back within 10 s: a microphone meter start (`microphone-ioproc`), the meter's stop for a hand-off to the processed microphone (`microphone-ioproc`, `reason=hand-off`), a system playback meter start or stop (`system-output-tap`, `id=0`), or a processed microphone capture start or release (`processed-microphone-capture-ioproc`). Nothing further is issued to that queue until the call comes back; treat it as `coreaudiod` not answering.
- `forget`: `coreaudiod` restarted, and the ID is dropped without a HAL call.
- `invalidate`: the framework reported a configuration change under an engine, whose line names the device it is bound to now, or a listener reported the system playback meter's aggregate device or tapped output dead or reconfigured (`system-output-aggregate`, once per build). Nothing is stopped for it; the owner rebuilds after the window.
- `give-up`: automatic rebuilds, retries, or publications stopped after repeated failures, written once. On the microphone meter's and the capture's lines, `transport=unread` means that input is no longer the default input the poll shows. `system-output-tap give-up id=0 transport=- status=0 gen=<n> output=<id>` comes at the eighth invalidation in a row with no 30 s run between, and `processed-microphone-publisher-engine give-up id=<output> transport=<class|unread>` at the fourth unusable output format read in a row on that output, after a `processing-invalidated` or `processing-refused` hold. After either, nothing is created, started, or stopped for that meter or for the processed microphone's capture and engines until Retry, switching the feature, or an output change; `quiet-window hold` lines can still appear. `processed-microphone-capture-ioproc give-up id=<input> transport=<class the poll shows>` comes at the eighth read in a row, made as the capture opened that input, that could not read its transport or could not resolve an aggregate member the poll had resolved; each of those reads wrote a `refuse` line, whose class shows what it read, such as `unread` or an aggregate device with `?`, followed by a `processing-refused` hold; a Bluetooth refusal writes no such hold. The processed microphone then shows failed with Retry, and no capture start follows until Retry or until it is switched off and on. `processed-microphone-aggregate give-up id=0 transport=- status=0 gen=<n> aggregate-uid=<the fixed UID>` comes when a quiet window has interrupted three publications in a row with none completed between them: at the first release after the third, `stops-only` included, after the rollback lines of what that publication kept. No create of a publication object follows until Retry, or until the processed microphone is switched off and on. `microphone-ioproc give-up id=<input> transport=<class the poll shows>` comes at the eighth start of the microphone meter in a row on that input that failed, or whose read of the device as it was opened could not read its transport or could not resolve an aggregate member the poll had resolved; those reads each wrote a `refuse` line followed by a `meter-refused` hold. Each of those starts released what it created before it reported, so the meter leaves nothing open. The menu bar shows `--`, the panel shows the meter's error with Retry, and no `microphone-ioproc create-begin` follows until Retry, another default input, a start of the processed microphone, or a `coreaudiod` restart; with the input unchanged, no timer, wake, device-list or default-device notification, or poll brings one. After Retry it follows from an evaluation that admits starts: at once when no window is armed, and otherwise after a `full` release.

The objects:

- `microphone-ioproc`: the microphone meter's IOProc; `id=` is the input device.
- `microphone-listener`, `processed-microphone-capture-listener`, `system-output-listener`, `system-listener`: written only as `create`, with the status, when a property listener could not be added. `id=` is the object it was to be added on, the HAL system object for `system-listener`.
- `system-output-tap`, `system-output-aggregate`, `system-output-ioproc`: the system playback meter's private process tap, its private aggregate device, and the IOProc on that aggregate device, whose `id=` is the aggregate device's. Their lines end with `output=<tapped output ID>` once the output has been read, and carry `aggregate-uid=io.github.yuhkis.audio-level-bar.tap.<UUID>` while the aggregate device exists and `tap-uid=` while the tap exists. `system-output-tap interrupt id=0` is also written when the rebuild's uncached read of the default output no longer matches the output it was issued for, or cannot be read; `quiet-window hold reason=output-moved` follows.
- `processed-microphone-tap`, `processed-microphone-aggregate`: the published process tap and aggregate device, “Audio Level Bar Microphone”, with the tap's `tap-uid=` and the fixed `aggregate-uid=`. `processed-microphone-aggregate destroy` with `reason=launch` removes a published device an earlier run left behind.
- `processed-microphone-probe-ioproc`: the IOProc on the published aggregate device that confirms the system audio recording permission after publishing.
- The publication is those three objects' calls, made one after another on the main thread: `processed-microphone-tap create`, `processed-microphone-aggregate create`, then `processed-microphone-probe-ioproc` `create`, `start`, `stop` about 100 ms later, and `destroy`. Every one of those lines carries the generation the publication was issued in, and that generation is compared immediately before each call. When a listener has advanced it, the publication writes `<object> interrupt id=<id, or 0 for an object not yet created> transport=- status=0 gen=<the generation it was issued in> reason=before-<create|start|stop|destroy>[ aggregate-uid=<uid>][ tap-uid=<uid>]` in place of that call's begin line, and no begin line of any publication object follows until a `quiet-window release`: no create or start, and no stop, destroy, or rollback either, the rollback of a publication that failed included. What it created stays, not published: the status does not show it as published, no engine starts for it, and other apps can already list the device, which carries silence. After `reason=before-stop` the probe's IO keeps running on the published aggregate device until that release, as a meter the window finds running does; its callback does nothing. The first release, `stops-only` included, rolls back what was kept with that release's generation, in the withdrawal's order: the probe's `stop` and `destroy`, where one exists, then `processed-microphone-aggregate destroy`, not made while a process has the device open, then `processed-microphone-tap destroy`. A window that arms during the rollback ends it with `interrupt-stop` and the same `reason=`, and the next release goes on from there. A new publication follows at a release that admits starts, in the same evaluation after a `full` release, if the processed microphone is still wanted and its source allowed. After the third interrupted publication in a row, `processed-microphone-aggregate give-up` follows the rollback instead, and no publication.
- `processed-microphone-capture-ioproc`: the processed microphone's capture with processing off or WebRTC; `id=` is the input device.
- `processed-microphone-publisher-engine`, `processed-microphone-voice-processing-engine`: the publisher `AVAudioEngine`, and Apple voice processing's capture `AVAudioEngine`. `id=` is the device the engine's node is bound to, read back from its audio unit: the output for the publisher, the input for voice processing. The voice-processing engine's lines also end with `output=<id>`, the device its unit's output element is bound to; the start binds the unit to the input and output it checked, once voice processing is enabled and before any format is read, and a bind that fails or reads back another device refuses the start with no tap, prepare, or start after it. `transport=` is the class read before the call, `moved` when the node is bound to a different device than expected, `unbound` when none was expected, and `unread` when the ID could not be read. `transport=` describes `id=` alone: a voice-processing line whose `output=` has moved keeps the input's class, and `output=0` is an output element that could not be read. The publisher writes `prepare-begin` and `prepare` after it is attached and connected, before `start-begin`; voice processing writes them after its tap is installed, before its default-device re-read and `start-begin`. An Apple start interrupted after its prepare leaves prepare lines and no start or stop lines for that engine, and the release after the window stops such an engine without stop lines. The publisher's build checks the quiet window's generation and the owner again immediately before its output is bound, before its prepare, before its start, and before the stop of a start that failed; a build stopped there issues nothing more and stops nothing, and the release after the window stops that publisher, with stop lines only if its start was issued. The engines' stop lines carry the generation the evaluation that issued the stop saw, or the start's for the stop of a start that failed; when that generation is no longer current, `interrupt-stop`, or `interrupt` for a stop a start makes, is written in place of `stop-begin`, as described above. An Apple start whose output reads no usable format after voice processing is enabled keeps that unstarted engine too, with a `processing-invalidated` hold, and the release after the window stops it.
- `processed-microphone-source`: the processed microphone refusing or abandoning its source. `refuse id=<default input>` for an input it does not capture, and `refuse id=<default output>` for Apple voice processing refused by the output. `refuse id=<lowest-numbered connected Bluetooth device> transport=<class from the pickers, or unread>`, written once when Apple voice processing becomes refused because a Bluetooth audio device is connected. `refuse id=<listed Bluetooth output> transport=bluetooth|bluetoothLE`, when the uncached read before an Apple start lists one, followed by `quiet-window hold reason=processing-refused`. `refuse id=<device a default moved to> transport=moved`, when a default device ID moved immediately before or after the voice-processing engine started; after a start it follows the engine's `start` line. A `processing-refused` hold follows at once, before any stop line, and what the start built, a started engine included, is stopped at the release after the window. `interrupt id=<input>`, when a window armed before or while the Apple start built its publisher, installed its tap, or started its engine, the uncached default-device reads immediately before the start included, or before a start that then failed. What an interrupted or moved Apple start built stays until the release after the window, which writes stop lines only for an engine whose start was issued.
- `reclaimed-tap`: `destroy-begin` and `destroy` of a process tap an earlier run left behind, with `tap-uid=` and `reason=launch` from the launch cleanup, or `reason=reclaim-command` from `--reclaim-taps`, which the gate does not use.

The reasons, each a fixed word:

- `quit`: every stop and destroy Quit issues, the engine stops and the publication withdrawal included; `gen=-`.
- `bluetooth-sub-device`: the `refuse`, `stop`, and `destroy` of a `microphone-ioproc` or `processed-microphone-capture-ioproc` whose open aggregate device gained an active Bluetooth sub-device; `gen=-`. It is a last resort that only an edit of the aggregate device while it is open can reach, since no aggregate device that names a Bluetooth member is opened, and the criteria do not exempt it.
- `bluetooth-selection`: the `stop-begin` and `stop` of both processed microphone engines that the app's own picker issues before it writes a default device that may involve Bluetooth; `gen=-`. They come before that pick's `input-selection` or `output-selection` hold and its `control-write default` line. The picker issues them only while no window is armed or carried, no default write is outstanding, no restart is owed, and no Bluetooth device is connected or unread; otherwise it writes `picker refuse` and neither stops nor writes.
- `failed-start`: the stop of IO that read running after an `AudioDeviceStart` that did not return `noErr`, on `microphone-ioproc`, `system-output-ioproc`, `processed-microphone-capture-ioproc`, or `processed-microphone-probe-ioproc`. It exempts nothing.
- `hand-off`: on a `microphone-ioproc stall`, above.
- `engine-raised`: on the `interrupt` of a `processed-microphone-source` (Apple voice processing) or `processed-microphone-capture-ioproc` start whose AVFAudio call raised an Objective-C exception, as AVFAudio does while a device is rebound under the engine. Nothing more is issued and nothing is stopped or freed; a `processing-invalidated` hold follows, and the release after the window stops what the start built. The fourth such start in a row with no started one between is also reported as a failure of the start. It exempts nothing.
- `before-create`, `before-start`, `before-stop`, `before-destroy`: on the `interrupt` of the processed microphone's publication and the `interrupt-stop` of the rollback of what it kept, the call that was held back. They exempt nothing.
- `launch`: the launch cleanup's destroys. It exempts nothing.
- `reclaim-command`: `--reclaim-taps`; `gen=-`.

`gen=` is the quiet window's generation the work was issued in, read once and carried on both lines of a call, or `-` for the three unheld operations above and for `--reclaim-taps`. The main-thread publication and its probe IOProc carry the generation the publication was issued in on every line, and the rollback of what an interrupted publication kept carries that of the release that issued it. The publication's owed teardown, the retry of a teardown left after switching the feature off, and the launch cleanup, which removes an earlier run's published device and then reclaims its stranded taps, carry the generation the evaluation that issued them saw and are compared against it immediately before each destroy, because each destroy follows work that can wait in `coreaudiod`: the engines' stop, a read of the device list, or the wait for a destroyed device to leave it. At a mismatch that destroy and the ones after it are not made, an `interrupt-stop` line names the object the next destroy was for (`processed-microphone-aggregate`, `processed-microphone-tap`, or `reclaimed-tap`), and the release after the window carries the rest out. Only Quit's teardown is not compared. A line that belongs to no issued call (`forget`, `invalidate`, `stall`, `give-up`, a poll-level `processed-microphone-source refuse`, a system object's listener failure) carries the generation current when it is written; the meters' and the capture's listener failures carry their start's.

A device's transport class is `builtIn`, `usb`, `bluetooth`, `bluetoothLE`, `aggregate`, `virtual`, `pci`, `fireWire`, `hdmi`, `displayPort`, `airPlay`, `avb`, `thunderbolt`, `continuityCapture`, or `unknown` for a transport read but not classified; `unread` when it could not be read, and `-` where none applies. An aggregate device reads `aggregate[<active sub-devices>|<full composition>]`, with nested aggregate devices replaced by their members, `?` for a member that could not be resolved (a device that is not connected, an unreadable transport or nested list, or nesting too deep or cyclic), and `unread` for a list that could not be read: `aggregate[builtIn|builtIn,bluetooth]`, `aggregate[builtIn|builtIn,?]`, `aggregate[unread|unread]`. `moved` and `unbound` appear as described for the engines and for `processed-microphone-source`.

The quiet window writes:

- `quiet-window hold reason=<reasons> release-in=<s.ss> gen=<n>`: the window armed or re-armed. `gen=` is the generation after the hold; a start or stop issued with an earlier one is abandoned before its next HAL call. The reasons are `launch`, armed before anything else at launch; from the poll, `default-input`, `default-output`, and `bluetooth-devices`, joined with `,` when several changed together, or `topology` when there was no previous poll to compare with; `input-selection` and `output-selection`, from the app's pickers at the pick and again when the write completes; `hal-notification` and `service-restarted`, from listeners on the HAL system object; `generation-advanced`, when an evaluation read a generation a listener had advanced before the main thread armed the window; `poll-slow`, for a poll in flight for more than 0.5 s; `launch-cleanup`, after the launch cleanup destroyed an earlier run's published device; `meter-invalidated` and `meter-refused`, for the microphone meter's listener invalidation and, at its open, a failed transport read or an aggregate member that read could not resolve although the poll had, which the meter retries after its delay; `processing-invalidated` and `processing-refused`, for a configuration change or an unusable output format under the processed microphone's engines and a start refused by a re-read, which the capture tries again after the meter's delay, 2, 4, then 8 s, and up to the meter's eight attempts, when that read only failed to read the input's transport or to resolve an aggregate member the poll had resolved; `output-invalidated`, `output-stale`, and `output-moved`, for the system playback meter's listeners, its levels not arriving for 4 s, and its rebuild finding the default output moved; and `carried`.
- `quiet-window advance source=<hal-notification|service-restarted> gen=<n>`: a listener advanced the generation on its own queue before the main thread armed the window. The hold line that follows carries a generation one higher.
- `quiet-window release mode=<full|stops-only> gen=<n> snapshot-age=<s.ss|-> writes-outstanding=<n> poll-in-flight=<true|false>`: an evaluation released the window. A `stops-only` release issues stops, destroys, and owed teardowns, and no create, prepare, start, publication, or processing start. `snapshot-age` is the time since the newest applied poll was issued, `writes-outstanding` the pickers' default-device writes not yet completed, and `poll-in-flight` whether a poll had not returned.
- `quiet-window hold reason=carried`: written after the steps a release issued synchronously, when a change was carried past the 15 s cap or a cap-forced release left part of a settle period. It does not advance the generation, so it repeats the release's `gen=`, and what that release issued to the lifecycle queues can be logged after it. A hold written with `release-in=0.00` noted a change at or after the cap: that change is carried, and the line is immediately followed, at the next evaluation, by `quiet-window release` and then `quiet-window hold reason=carried`, which opens the carried change's window.

Other lines:

- `hal-poll slow issued-ago=<s.ss> gen=<n>`: once per poll, when a tick is dropped more than 0.5 s after the poll in flight was issued, together with `quiet-window hold reason=poll-slow`. `hal-poll recovered elapsed=<s.ss> gen=<n>`: immediately before the result of such a poll, or of one that took more than 0.5 s, is applied.
- `control-write <default|volume|mute> id=<device> direction=<input|output> transport=<class|unread> status=<OSStatus> queued=<s.ss> elapsed=<s.ss> gen=<n>`: a default-device, volume, or mute write finished on the HAL worker's queue.
- `picker refuse id=<device> direction=<input|output> transport=<class|unread|-> gen=<n>`: the app's own picker did not take a pick of a device that may involve Bluetooth, because Apple voice processing was engaged while a change could be under way: a window armed or carried, a generation the main thread had not armed for, a default write outstanding, a restart owed, or a Bluetooth device connected or unread. Neither the engines' stop nor the default write was issued, and the picker shows the current default again. `transport=-` is a device the picker's list does not show.
- `power will-sleep gen=<n>` and `power did-wake gen=<n>`: the system's sleep and wake, logged only.
- `quit-deferred release-in=<s.ss> gen=-`: Quit arrived while the window held, or a wait it deferred came due and the window had noted a change since. The menu bar item is already gone, and the teardown waits this long: until 3 s after the last change the window noted, a carried one included, never later than 3.00 s after the request, and until then while a picker's default-device write is outstanding. The first is written at the request and each later one as the previous wait ends; all come before any `reason=quit` line. After a Quit request, deferred or not, no `quiet-window release`, `hal-poll`, `control-write`, or evaluation-issued lifecycle line is written; `quiet-window advance` and `quiet-window hold` lines from listeners can still appear and change nothing.
- `quit lifecycle-stops completed=<true|false> pending=<queue>:<phase>[,...] waited=<s.ss> gen=-`: Quit's wait for the stops it hands to the lifecycle queues, after the deferral and after the main-thread publisher stop and publication withdrawal. It waits while some queue has finished a HAL call within the last 3 s, and at most 8 s; `completed=false` means it gave up, and the process exits anyway. The queues are `microphone`, `system-output`, and `processed-capture`; the phases, each the call a queue had not yet passed, are `queued`, `remove-listeners`, `read-is-running`, `stop-ioproc`, `destroy-ioproc`, `destroy-aggregate`, and `destroy-tap`. `waited=` does not include the deferral.

#### Pass criteria

Cut each cycle out between its markers and judge it against every criterion. One miss in one cycle fails the configuration; the `third-party-mic` cycle is report only.

The terms used:

- The app's lines are those whose `processID` is the installed app's PID from the latest `app-pid` marker. A `coreaudiod` IO context is the app's when any captured line ties its context ID, which `IOWorkLoopInit` prints first, to the app: a `BluetoothHALPlugIn_register`, `BluetoothHALPlugIn_StartIO`, or `BluetoothHALPlugIn_StopIO` line of `coreaudiod` that carries it as `clientID=` with the app's PID in `PID=`; a line from the app's own process (its `processID` is the app's PID; `coreaudiod`'s lines of the same names do not count) that names it, as `HALC_IOContext_PauseIO(<context>)`, `HALC_IOContext_ResumeIO(<context>)`, and the `HALC_ProxyIOContext::PauseIO` and `ResumeIO` lines with `id:<context>` do; an `IOWorkLoopInit` that criterion 9 matched to an app start line; or an `IOWorkLoopInit` that names the app's PID, as in `CADefaultDeviceAggregate-<pid>`, or a UID from an app `aggregate-uid=`. The first two are what shows IO that a framework started inside the app's process, which no app `start` line goes with. A context on a Bluetooth input or output that no captured line ties to any PID counts as the app's.
- A request is the `HandlePlugIn_RequestConfigChange` lines that one `coreaudiod` thread ID writes, in order: `--->`, `--- calling driver`, `--- driver returned`, `--- restarting IO` when IO restarts, and `<---`. Pair them by thread ID, never by line order: requests on different threads interleave, and their `<---` lines come back in any order. Criteria 4, 6, and 7 measure a request on its own thread. A `--->` whose thread writes another `--->` before its `<---`, or no `<---` by the cycle's end marker, fails. The `PauseIO` lines of a request's burst and the `ResumeIO` lines of its resume pass are written on other threads, so tie them to the request by time: the burst falls between its `--->` and its `calling driver`, and the resume pass follows its `restarting IO`. A burst that falls inside two requests' intervals belongs to both.
- A Bluetooth request is a request for a Bluetooth device. `coreaudiod` redacts the device in the request lines themselves, so attribute each request from the `BluetoothHALPlugIn_` and `HFPInputShimDevice` lines on its thread, or immediately around its `--->`; the `Requesting config change` and `Starting config change` lines name the Mac's own devices. A request that cannot be attributed while a Bluetooth device is changing counts as a Bluetooth request. A request's span runs from its `--->` to its `<---`, and on through the `ResumeIO` lines of the resume pass that its `restarting IO` begins.
- A Bluetooth burst is the run of `PauseIO` lines a Bluetooth request's `PauseAllContexts` writes.
- An app call's interval runs from its begin line to its result line. A begin line with no result line is in flight until the end of the cycle.
- A request spans sleep when its `--->` comes before `coreaudiod`'s `Received power notification: Sleep` line, or within 1 s after it and before the wake anchor, and its `<---` comes after the wake anchor. The requests sleep itself makes, for the Mac's own devices, begin a few milliseconds to a few hundred milliseconds after that line, reach `calling driver` at once, and return only after wake. The wake anchor is the first `NewState: DarkWakeEntitledIO` or `NewState: FullWake` line after that Sleep line: there `coreaudiod` begins to resume IO, and the first `HALC_IOContext_ResumeIO` line of the wake follows. The `Received power notification: DarkWake` line with `Early Wake: Yes` comes a few hundred milliseconds before it and is not the anchor, and the `FullWake` notification comes after the requests have returned. When the Mac goes back to `NewState: Sleeping` before the request's `<---`, as a wake that never reaches full wake does, the anchor is the one after the last such line. Criteria 4, 6, and 7 time such a request from the anchor instead: a `calling driver` not reached before sleep within 2 s of it, the `<---` within 150 ms of it or of a `calling driver` after it, whichever is later, and 50 ms from it to `calling driver` when the burst pauses an app IO context. A request that has not reached `<---` by the cycle's end marker fails. Every other criterion judges the request and its span in full, criteria 2 and 3 included.

The criteria:

1. No app IO on a Bluetooth input or output: no `IOWorkLoopInit` for a Bluetooth input or output in an app IO context, whether or not an app `start` line goes with it; no `BluetoothHALPlugIn_register` or `BluetoothHALPlugIn_StartIO` with the app's PID, and no HFP input shim start for the app; no `CADefaultDeviceAggregate-<app PID>`, no AUHAL or AVFAudio default-device aggregate lines from the app, and no `VPAUAggregateAudioDevice`, `AUVPAggregate`, or `AUVoiceIO` line from the app that names the headset; and no app `start`, `prepare`, `stop`, or `invalidate` line, nor any pause or resume of an app IO context, on a Bluetooth input or output. The device of an app line is its `id=`, and for the voice-processing engine its `output=` as well, whatever `transport=` says, `moved` and `unread` included. An engine line that reads `moved`, or a voice-processing engine line whose `output=` differs from its `start` line's (`transport=` follows `id=` alone and does not show it), fails unless the same cycle shows that ID to be a device that is not Bluetooth, by an app line that carries it with such a class or a `coreaudiod` line that names its device; an ID that cannot be resolved counts as Bluetooth, and a later `make diagnose` does not resolve it, because a Bluetooth device gets a new ID each time it connects. The one exception is the documented residual, the system playback meter's tap and private aggregate device while the default output is Bluetooth, a plug-in line whose `clientID=` is the context of its `system-output-ioproc` included; every other criterion still judges their calls. This holds in ③b-Apple as in every other configuration.
2. No app call in flight when a Bluetooth burst begins: no app `start`, `prepare`, `stop`, or `destroy` interval contains the first `PauseIO` of a Bluetooth burst, and no app begin line of any operation falls between a Bluetooth request's `--->` and `<---`.
3. No app stop or destroy across a Bluetooth request: no app `stop` or `destroy` interval, whatever its `reason=`, `quit` and `bluetooth-sub-device` included, overlaps a Bluetooth request span.
4. No `PauseAllContexts: still waiting`, and every `RequestConfigChange` reaches `calling driver` within 2 s, timed from the wake anchor for a request that spans sleep.
5. No `StartAndWaitForState returned error` from the app, whatever the code, except `nope` right after a device-only request whose driver returned `!obj`. Error 35 counts in every configuration, ③b-Apple included.
6. No app-attributable request stall: no more than 150 ms from a request's `--->` to its `<---`, timed from the wake anchor for a request that spans sleep. Stalls attributable to other apps are reported, not failed.
7. No more than 50 ms from the last `PauseIO` of a burst to `calling driver`, or from the wake anchor for a request that spans sleep, when the burst pauses an app IO context. A longer gap on a burst with no app IO context is reported, not failed.
8. Every tap `unregister_meta_device` is followed within 1 s by `_Deactivate` of the same ID on the same thread, and no app tap registers or unregisters inside a Bluetooth request span.
9. Every app `start` line matches a `coreaudiod` `IOWorkLoopInit` on the intended non-Bluetooth device: the meter's or the capture's input, the publisher engine's bound output, the voice-processing engine's input, or, for `system-output-ioproc` and `processed-microphone-probe-ioproc`, the aggregate device the line names, whose UID `IOWorkLoopInit` prints and the line carries as `aggregate-uid=`: the private aggregate device for the system playback meter, and the published “Audio Level Bar Microphone” for the probe. For the two engines, the `IOWorkLoopInit` may fall inside the engine's `prepare-begin`..`prepare` bracket or its `start-begin`..`start` bracket.
10. Nothing inside a quiet window, judged by `gen=` rather than by line order. After a `quiet-window hold` or `quiet-window advance` line with generation H, no app `create`, `prepare`, `start`, `stop`, or `destroy` begin line carries a `gen=` below H, and none carries `gen=H` before a `quiet-window release` with `gen=H`. The main-thread publication is judged like every other call, with no count of its own and no exemption: each of its begin lines carries the generation it was issued in, and a publication that a listener's advance interrupts writes an `interrupt` line and issues nothing more, neither a create or start nor a stop, destroy, or rollback, until a release. `quiet-window hold reason=carried` does not advance the generation: begin lines after it that carry the preceding release's `gen=` are that release's work, which criterion 11 judges. Of the `gen=-` lines, only two kinds are exempt: `reason=bluetooth-selection`, and `reason=quit` no earlier than the last `quit-deferred` line's time plus its `release-in`. With no `quit-deferred` line, the `reason=quit` lines fail when a `quiet-window advance` line, or a `quiet-window hold` line other than `reason=carried`, comes less than 3.00 s before the first of them: Quit should have deferred. A `reason=bluetooth-sub-device` line while a window is armed fails.
11. A `quiet-window release mode=stops-only` is followed by no app `create`, `prepare`, or `start` begin line, and no publication of the processed microphone, before the next `quiet-window release mode=full`.
12. Every `quiet-window release mode=full` shows `writes-outstanding=0`, and `snapshot-age=` of at most 0.75 unless polls were slow around it: a release with a larger age does not fail when a `hal-poll slow` or `hal-poll recovered` line comes between the window's first hold and 1 s after the release, and is recorded with its age and those lines instead.
13. No `stall` line of any object, and the menu bar and panels never show that Core Audio has not finished starting or stopping while `make diagnose` answers.
14. Every Quit: every `quit-deferred` line, when written, before any `reason=quit` line, with the last one's time plus its `release-in` no later than the first one's time plus 3.00; `quit lifecycle-stops completed=true pending= waited=` below 1; the process exits; and `make diagnose` then lists no published device or tap of the app, except in `relaunch-recording` while QuickTime Player still records.
15. `make diagnose` reports Core Audio answering after each block.

Judge the behavior along with the log: the menu bar shows `--` within one poll after the headset becomes the default input; the meter resumes on the previous microphone after the quiet window once the headset leaves; the system playback meter resumes; the processed microphone shows the Bluetooth refusal, keeps its publication, and starts or resumes by itself, without Retry, once the headset leaves; and ③b-Apple meets the expectations of its headset cycles above.

#### Checks recorded with the gate

Examine these before calling the gate passed. None is expected on healthy hardware, and each needs its cause understood:

- a `give-up` line, the microphone meter's `microphone-ioproc give-up` and the publication's `processed-microphone-aggregate give-up` included;
- a stop with `reason=failed-start`;
- a `bluetooth-sub-device` line outside a window, which only an edit of an open aggregate device should reach, and the gate makes none;
- an engine `invalidate`, `stop-begin`, `stop`, `interrupt`, or `interrupt-stop` line whose `id=`, or for voice processing `output=`, differs from that engine's `start` line while the same cycle shows the device it names not to be Bluetooth: the node followed a device despite its binding. When the device is Bluetooth or cannot be resolved, criterion 1 fails it instead;
- a `VPAUAggregateAudioDevice`, `AUVPAggregate`, or `AUVoiceIO` line from the app between the headset's connection and the voice-processing engine's stop lines, which would show the bound unit rebuilding itself on a device change; record what it names;
- `com.apple.coreaudio.avfaudio` or `required condition is false` in a capture or in `~/Library/Logs/DiagnosticReports`.

Confirm these on hardware, or record them as unconfirmed:

- The resume pass: which `ResumeIO` lines follow a request's `restarting IO`, on which threads, and which line ends the pass; and that a request's `BluetoothHALPlugIn_` and `HFPInputShimDevice` lines are written on the request's own thread. `coreaudiod` is expected to write `HALC_IOContext_ResumeIO(<context>)` and `HandlePlugIn_RequestConfigChange: ... --- restarting IO` lines; confirm them on the first cycle. Confirm too that the `--->`, `calling driver`, `driver returned`, and `<---` lines of one request share a thread ID, which the terms assume, and which process writes the `HALC_IOContext_PauseIO(<context>)` and `HALC_IOContext_ResumeIO(<context>)` lines, `coreaudiod`, the client, or both: only a client's own line ties a context to that client.
- Whether `IOWorkLoopInit` prints the tap's UID in the form `tap-uid=` carries. The app logs the `CATapDescription` UUID in uppercase; the aggregate device's UID is printed.
- For each engine, whether its `IOWorkLoopInit` falls between `prepare-begin` and `prepare`, or between `start-begin` and `start`; and, for voice processing, whether it names the bound input itself or a `VPAUAggregateAudioDevice` that wraps the bound input and output. Criterion 9 and `preflight` expect the input.
- In `preflight`, that the muted process tap still captures a publisher bound to the built-in output, in all three modes.
- In `aggregate`, that an absent headset member resolves to `?`, and that the full sub-device list of an aggregate device made in Audio MIDI Setup is readable. The poll writes no line, so this is confirmed only when a lifecycle-queue `refuse` or `open-unverified` line shows the class.
- In `settings`, that `quiet-window advance source=hal-notification` and `quiet-window hold reason=hal-notification` come before the poll's `default-input` hold for the same switch, and that no `interrupt` line after that hold shows an abandoned create. The notification narrows the gap; whether it arrives before the Bluetooth change begins is not known.
- Whether the HAL sends default-device notifications with unchanged values around the app's own creates and starts, seen as `quiet-window advance source=hal-notification` right after an app create or start with no device change. One that lands inside a publication interrupts it, and three interrupted publications in a row end in `processed-microphone-aggregate give-up`. Record its count per block, with the counts of publication `interrupt` lines, of `generation-advanced` and `poll-slow` holds, of `hal-poll slow` and `hal-poll recovered` lines, and of full releases with `poll-in-flight=true`.
- In ②, no `output-invalidated` hold right after a `system-output-ioproc start` with no device change, no repeating rebuild, and no `output-stale` hold while audio plays; and whether a `system-output-tap interrupt` followed by `quiet-window hold reason=output-moved` appears in the headset cycles.
- In `third-party-mic`, whether the headset's profile switch fires `system-output-aggregate invalidate` and `output-invalidated` holds more than once, and whether the rebuild waits until 3 s after the last.
- In ③b-Apple, that the interface does not visibly stall around each voice-processing engine start, where the default devices are read on the main thread, and that the refusal text appears in the app's language with the orange status and no Retry.

- If a `meter-refused` hold appears, that the meter's next start comes after the window and its delay rather than at once; and the same for the capture's next `create-begin` after a `processing-refused` hold that follows a `processed-microphone-capture-ioproc refuse`.

Report the cycle counts per configuration and block, the devices that were unavailable, and which results come from the source, the candidate, the installed app, or real-device verification. Survival counts are reported but are not pass criteria.

#### If coreaudiod stops answering

Do not force quit the app, do not remove any aggregate device, and do not restart first. Leave the capture running, mark the moment with `/usr/bin/logger "ALB-GATE <config> <block> cycle <n> hang"`, capture `sudo spindump coreaudiod` and `sudo sysdiagnose`, and only then restart the Mac.

## Build and installation

When preparing a deployment candidate:

1. Bump `CFBundleVersion` in `Resources/Info.plist`, and commit the code, its documentation, and the bump together before building.
2. Run `make app`, then `make verify-app` against `dist/Audio Level Bar.app`.
3. Carry out the real-device verification the change calls for against that candidate.
4. Quit the app normally, run `make install`, and verify the installed app. [Installing and everyday use](../README.md#installing-and-everyday-use) covers the separate login-agent step, and what to confirm when the same bundle is carried to more than one Mac.

`make app` embeds the commit SHA, the clean/dirty state of the working tree, a source fingerprint, and a provenance timestamp. The fingerprint covers every tracked file and every untracked file that is not ignored, documentation included. `scripts/build-app.sh` compares the commit, the state, and the fingerprint against a bundle already in `dist/` that carries the same version and build number, and refuses to reuse that pair for a different snapshot; with no such bundle there is nothing to compare against, which is why a fresh CI checkout is unaffected. Building before committing therefore spends a build number on the previous commit and a dirty tree, and the committed bundle then costs a second one to say the same thing — commit first.

The build number identifies a deployment candidate, not a commit:

- Bump it for a change that is going to be built, verified on hardware, and installed, and commit the bump with the change it covers.
- A commit that builds and installs nothing — a documentation-only change, for instance — needs no bump. `make ci` builds the app, so running it again locally while `dist/` still holds a candidate carrying the same build number is refused whatever changed; remove `dist/` and run it again rather than spending a build number, and build the candidate again when the next one is actually being prepared.
- A pull request from outside the project is the exception in both directions: it leaves `CFBundleVersion` alone and removes `dist/` between local runs, so that concurrent pull requests do not conflict on that one line, and the maintainer bumps the build number when the next deployment candidate is prepared.

`make app` signs ad hoc by default. `CODESIGN_IDENTITY` names a certificate explicitly; one is never selected automatically from the keychain, which may hold a certificate issued to someone else (the same contract as wkr-macos). A certificate signature adds the hardened runtime and the audio-input entitlement it requires. [Building and running](../README.md#building-and-running) has the command and the signature verification contract.

`make install` refuses while the app is running. Quit it through its own Quit item or run the command below. The process can outlive its menu bar item by a few seconds, while its teardown waits out a quiet window and then the lifecycle queues:

```console
osascript -e 'tell application id "io.github.yuhkis.audio-level-bar" to quit'
```

Never force quit while the processed microphone is published; that is one of the ways to leave Core Audio wedged for the whole machine.

## Localization

User-facing text goes through `localized(...)` from `Sources/AudioLevelBarCore/Localization.swift`. The key is the English wording, so a bundle without a translation, a `swift run` build, and the tests all fall back to readable English. Add the Japanese to `Resources/ja.lproj/Localizable.strings` and the identity entry to `Resources/en.lproj/Localizable.strings` in the same change; `make check-localization` fails on a key missing from either table, used by nothing, or whose English table entry is not identical to its key.

Keep the key and the opening `localized(` in one expression that a newline-folded grep can find, and do not use a multi-line string literal as a key — the extractor in `scripts/check-localization.sh` will not see it.

`AudioDiagnostics` and `AudioResourceInventory` are the `--diagnose` and `--reclaim-taps` command line output. They run outside the app bundle, where no string table is available, so their text stays English and is not localized. The Japanese substrings in `AudioDeviceSymbol` are device-name matching patterns, not display text.
